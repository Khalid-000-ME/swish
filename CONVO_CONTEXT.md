Worth clarifying up front: nothing has actually been built yet — this is the flow as specified in the Tokyo migration PRD. Here's how money and trust actually move through the system, end to end.

The shape in one sentence
An AI agent looks at a shop's revenue and recommends bond terms. It cannot act on its own recommendation. A backend converts that recommendation into an on-chain object, a human independently seals it through World, and only when both objects exist together can a bond come into existence on Sui. After that, the bond runs itself.

Stage 1 — Underwriting (off-chain, nothing has touched the blockchain yet)
A shop applies to issue a bond. The backend calls the underwriting agent, which is required by its system prompt to call four tools in a fixed order:

analyzeRevenue(issuerId) — pulls the shop's trailing 90-day revenue, volatility score, and history length. In the current spec this reads from a labelled synthetic fixture (revenue-fixture.ts), not a live payment processor — disclosed, not hidden.
checkExistingDefaults(issuerAddress) — queries the on-chain BondRegistry for this issuer's IssuerStanding object, to see if they've defaulted on anything before.
recommendTerms(...) — this is the only step that touches money math, and it calls a plain deterministic function (computeDiscountRate, classifyDecline) — not the LLM doing arithmetic. The agent's tool call wraps a pure function; the rate it recommends is independently verifiable, not just "whatever the model said."
screenCounterparty(address, chain) — a live call to Intercepta, checking the issuer's own address for sanctions/scam exposure before anything proceeds.
The agent then narrates its reasoning in plain language and ends with an explicit line: it cannot issue the bond itself. That's the whole point of this stage — it produces a recommendation, not an action. Nothing has been written to any chain yet.

Stage 2 — The recommendation becomes an on-chain object
The agent's output (approved/declined, recommended coupon rate, reason code) is not written to Sui by the agent or by the frontend. A trusted backend process, holding an AgentCap capability object, calls mint_verdict() in underwriting_verdict.move, which creates an AgentVerdict object on-chain containing the recommendation.

This distinction matters: the LLM never holds a key that can write to the chain. The backend does, and the backend only mints a verdict after the agent's tool-call sequence completes — it's translating a recommendation into a fact, not letting the model act directly.

Stage 3 — The human seal
The shop owner (or whoever's authorizing issuance) sees the agent's recommended terms on screen and initiates World ID for Agents' fresh-verification flow — a redirect, not a widget. This is a different World product from IDKit: it's OIDC-shaped. The human authenticates, right now, specifically for this bond.

The callback is handled server-side only — this is a hard requirement from World's track, not just good practice: the frontend never receives anything it could forge a "verified" result from. Once the backend validates the callback, it signs a message (bond_id, a hash of the human's pairwise identifier, a timestamp) with its own key and calls mint_world_approval(), which verifies that signature on-chain via ed25519_verify and mints a WorldApproval object.

If the human cancels or the window expires, no object gets minted — the bond simply never comes into existence. That's the required denied/expired path, and it's not a special case in the code, it's just the absence of the object.

Stage 4 — Issuance: two objects, consumed together, or nothing happens
issue_bond() in bond_registry.move takes the AgentVerdict and the WorldApproval as arguments and destructures both — meaning they're deleted, permanently, the instant this function runs. It asserts the verdict says approved, and that both objects reference the same bond_id (so you can't staple an approval for one bond onto a verdict for another). Only then does it call bond::create_bond(), which produces a real Bond object with its face value, coupon rate, coupon schedule, and maturity baked in as intrinsic fields.

There is no code path where a bond gets created from a verdict alone, or an approval alone. Both have to exist, for the same bond, in the same transaction, and after issuance neither exists anymore to be reused.

One thing genuinely unresolved in the current spec, worth flagging honestly: issue_bond() returns the freshly created Bond object but the PRD doesn't yet specify what happens to it next — whether it gets transferred to the issuer's address or made a shared object. For the secondary market to work (multiple parties building transactions that reference the same bond), it almost certainly needs to be a shared object, not owned outright by the issuer. That's a Day 1 decision to nail down before writing bond_market.move.

Stage 5 — The bond lives on its own
Once issued, nothing needs to "run" the bond. Anyone — not a keeper, not a bot, literally anyone with an RPC connection — can call is_coupon_due(bond, clock), which just compares the current time against next_coupon_due_ms. When it returns true, a settlement function (in the not-yet-fully-coded coupon.move) does three things in one transaction: screens the payout counterparty through Intercepta, transfers the coupon amount, and calls record_coupon_paid(), which advances the bond's internal schedule and updates the issuer's IssuerStanding (on-time or late).

At maturity, is_matured() becomes true the same way, and a redemption function returns the principal and flips the bond's status to redeemed.

Stage 6 — Trading, gated by the same compliance logic
The secondary market lets someone resell a bond they hold. The transfer only succeeds if the recipient passes whatever holder-verification check the market contract enforces — the demo deliberately includes a rejected transfer from an unverified address, so the compliance gate is provably real rather than asserted.

Stage 7 — The register is just a read
Nothing in /register computes anything new. It queries the IssuerStanding objects that Stage 5's settlement calls have been updating all along — bonds issued, coupons on time, coupons late, defaults. It's a live reflection of on-chain state, which is also literally the Curvegrid Dashboard track's own submission requirement.

The trust boundary, stated plainly
The LLM never signs anything and never has spending authority. Every number it produces either comes from a deterministic function it called as a tool, or gets independently re-checked (Intercepta) before money moves. The only two things capable of bringing a bond into existence are a backend-minted verdict and a backend-validated human approval, and the chain enforces that both must be present and must agree with each other.
